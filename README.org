Fixed in v1.11. Files touched: =content-script.js=, =style.css=,

Two root causes, two fixes:

1. *Stuck ew-resize cursor after release* — the old code only set
   =body.style.userSelect= during drag; the visual =ew-resize= cursor came
   solely from the handle element's CSS. But while dragging the mouse
   could leave the 8px-wide handle, and the =mouseup= listener on
   =document= sometimes never fired (mouseup events get swallowed when
   the cursor is over an iframe / Netflix-owned overlay). Rewrote
   =setupResize()= to use *pointer events* with =setPointerCapture()=
   on the handle, so all subsequent =pointermove= / =pointerup= are
   guaranteed to reach the handle even outside its bounds. Also set
   =body.style.cursor='ew-resize'= during drag so the cursor is
   consistent the whole way, and explicitly clear it on =pointerup= /
   =pointercancel=. Added a duplicate =pointerup= listener on
   =document= as a belt-and-suspenders to release the drag if the
   handle ever loses pointer capture.

2. *Double-click not seeking* — the previous click handler was
   indiscriminately routing every click on the =<dl>= to
   =clickedWordORSent=, which treats a TIME-element target as a
   sentence and calls =translateSentence(<time>)= on it (sending the
   timestamp string to Google Translate, eating the gesture). The
   dblclick handler was there but the preceding two click events on
   the timestamp had already mutated state in a way that masked it
   on the user's side. New behavior:
   - Click on the timestamp =<time class="nst-ts">= seeks directly
     (single-click, the more discoverable gesture) and never falls
     through to the translation path.
   - Double-click anywhere on the row still seeks (as originally
     requested), via the row's =dblclick= listener.
   - Click on a word/sentence elsewhere in the row still translates.
   Added =LOG=s on =getVideoTime/seekVideo/dblclick/timestamp-click=
   so future regressions are visible in the DevTools console.

Also simplified =getVideoEl()= to just =document.querySelector('video')=
(the =.VideoContainer video= compound was an over-specific guess that
could miss on current Netflix DOM).

*Follow-up (v1.12):* the v1.11 seek path worked mechanically
(=video.currentTime= was set), but Netflix interpreted the direct
=currentTime= write as a tampered media event and bounced the user to a
"Pardon the interruption / Sorry, we're having trouble with your request"
error page (also visibly tearing =.player-timedtext= down, which the
log showed as =launched=false= polls immediately after the seek).

Switched to Netflix's *own* in-page player API. =injectNetflixSeekBridge()=
injects a one-shot =<script>= tag into the page context (so it can read
=window.netflix=, which is invisible to the content-script's isolated
world). The bridge listens for =postMessage({__nst:'seek', sec})= and
calls =netflix.appContext.state.playerApp.getAPI().videoPlayer
.getVideoPlayerBySessionId(<watch-session>).seek(ms)=. =seekVideo()= in
the content script now just =postMessage='s and waits for the
=seek-result= echo (logged as =[NST] seek-result: {ok, via}=). This
performs an in-place seek without tearing the player down — no more
=currentTime= setter, no more "Pardon the interruption".
